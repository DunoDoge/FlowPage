# Design

## Context

引擎与数据层逻辑经设备端全量用例（185/185，含文件夹上传/LWW/墓碑）证实正确；缺陷根因在传输层与调度（见 proposal.md - Why）。现状关键事实：

- `WebDavTransport.request()` 每请求新建 `http.createHttp()`，任何非 2xx 由调用方（`collectionPut` 等）抛 `PUT_<code>` / `PROPFIND_<code>`，网络异常抛 `NET_<code>`，均无重试；响应头已在 `WebDavResponse` 汇聚（`etag`），但未读 `Retry-After`。
- `SyncEngine.run()` 顺序：墓碑对账 → 书签 `syncCollection`（SyncEngine.ets:345）→ 文件夹 `syncCollection`（:384）→ 墓碑上传。
- PUT 响应缺 ETag 头时 `collectionPut` 会追加一次 PROPFIND `stat()` 回填，单实体最多 2 个请求，放大突发请求量。
- `SyncErrorText.write()` 仅覆盖 401/403/409/412，无 429。

## Goals / Non-Goals

**Goals:**

- 瞬时失败（429/502/503/504、NET_*）在传输层自动重试并收敛为成功，重试耗尽才计失败。
- 批量上传/下载触发服务商限流时：自适应节流把请求流压到服务商可接受节奏，熔断早停保证单轮最坏时长有界，剩余条目下轮续传。
- 文件夹集合先于书签集合上传，消除限流场景下文件夹饥饿。
- 重试决策逻辑可离线（设备端纯逻辑）测试；失败注入可在 FakeTransport 层测试。
- 保持 LWW/If-Match/墓碑语义、远端目录结构、记录 schema 与配置存储完全不变。

**Non-Goals:**

- 不引入并发上传、跨轮持久化的请求配额或同步进度 UI（进度条/百分比）。
- 不改 `http.createHttp()` 每请求新建的连接模式（非根因，ArkTS http API 约束）。
- 不做实体级分批断点续传（同步中断后靠 dirty/远端清单重扫，既有语义已够）。
- 不处理服务商小时级配额耗尽（表现为持续限流，由 D7 早停 + 友好文案兜底）。

## Decisions

### D1 重试位置：传输层 `request()` 内统一重试

- **选定**：在 `WebDavTransport.request()` 内重试。所有动词（PROPFIND/MKCOL/PUT/GET/DELETE）经同一入口，一处覆盖启动连发与逐实体上传。
- **备选 1——引擎层在 `hooks.put` 外重试**：否决。漏掉 MKCOL/PROPFIND/DELETE 失败（启动阶段与墓碑删除同样会被限流），且引擎需区分错误类型，侵入 `EntityHooks` 契约。
- **备选 2——SyncPage 整轮失败后自动重跑**：否决。粒度太粗：一轮数百请求只为重试末尾几条失败；`BUSY` 防重入与 `setLastSync` 时序都会被放大。

### D2 重试判定与节奏：单请求退避（零星瞬时失败）

- **选定**：可重试集合 = HTTP 429/502/503/504 + 网络异常（`NET_*`）；最多 3 次尝试；退避 500ms → 1000ms → 2000ms；响应含 `Retry-After` 秒数时以其为准，超过 5000ms 上限直接放弃本轮该请求。
- **备选 1——固定请求间隔（主动 pacing，如每请求 ≥200ms）**：否决。惩罚所有服务器（自建 Nextcloud 无限流却整体变慢），且阈值因服务商而异、无据可依；被动退避只在服务器明确施压时减速，自适应且零成本。（5.2 真实验收暴露批量风暴后，以 D6 的**事件触发式**自适应节流补充——仅在观察到限流后介入，正常服务器仍零成本，与固定主动 pacing 不同。）
- **备选 2——指数退避到更长（5 次尝试 / 8s 间隔）**：否决。重度限流下单实体最坏等待被拉长到 30s+，300 条批量下同步总时长失控；3 次 × 退避已覆盖绝大多数瞬时 429/502 窗口。
- **备选 3——并发上传 + 信号量**：否决。加剧限流而非缓解，且破坏墓碑/ETag 串行时序。

### D3 可测性：抽出纯逻辑重试决策类 `WebDavRetryPlanner`

- **选定**：新增 `entry/src/main/ets/core/sync/WebDavRetryPlanner.ets`：输入（尝试序号、状态码或网络错误标记、`Retry-After` 值），输出（等待毫秒数或放弃）。纯函数、无 IO，设备端用例直接覆盖退避序列、Retry-After 优先、5s 上限、非瞬时码不重试。`WebDavTransport.request()` 按其输出 `setTimeout` 等待后重发。
- **备选——只靠真实服务器手动验收**：否决。退避/上限边界在真机上不可稳定复现（限流窗口随机），回归无门禁。
- 说明：不把 `request()` 改造成可注入 transport 的接口（SyncTransport 已是 FakeTransport 的注入点）；FakeTransport 在引擎层测「失败 N 次后成功」的等价场景（引擎对重试耗尽的处理），重试本身的边界由 Planner 用例覆盖。

### D4 调度顺序：文件夹集合先于书签集合

- **选定**：`SyncEngine.run()` 中把文件夹 `syncCollection` 提到书签之前；墓碑对账仍在两个集合之前、墓碑上传仍在最后。
- **备选 1——公平交替（书签/文件夹轮转各 1 条）**：否决。破坏 `syncCollection` 的整体性（远端清单/本地清单一次装载），引擎复杂度陡增。
- **备选 2——每轮上传配额（如先传 100 条，其余留 dirty）**：否决。用户感知「同步了但没传完」，且需要额外状态决定下一轮优先级；重试退避已解决书签侧成功率。
- 顺序对书签/文件夹乱序到达无影响：书签先到、文件夹迟到已有 `restoreChain` 兜底与用例（`bookmarkArrivesBeforeFolderStaysVisible`）。

### D5 失败报告：沿用现有结构，补 429 文案

- **选定**：`SyncErrorText.write()` 增加 429 分支（「请求过于频繁（429），已自动重试仍失败，请稍后再同步」）；`SyncReport` 增加 `throttled` 布尔（D7 提前结束时置位，驱动汇总文案）。
- **备选——报告新增 retried 计数并在 UI 展示**：否决。重试成功本应无感，暴露内部细节徒增 UI 改动；`firstFailure` 已能携带 429 文案供用户辨识。

### D6 限流自适应节流：事件触发式 AIMD 节流器（5.2 验收反馈）

背景：真实验收（坚果云，远端 366+ 条）暴露「下载风暴」——逐条 GET 突发触发服务商 ~1 req/s 限流，每条失败再烧 1.5s 退避，366 条失败 ≈ 10–20 分钟纯等待且限流窗口永不恢复。单请求退避（D2）只适合零星瞬时失败，扛不住批量。

- **选定**：`WebDavPacer`（与 Planner 同文件的纯逻辑类）挂在 `WebDavTransport` 上，全请求域共享：任一请求重试耗尽于 429/503 后激活，基础间隔 1000ms（`Retry-After` 有值时取 `max(1000, min(Retry-After, 30000))`），此后每个请求前等待该间隔；每次成功将间隔 ×0.8（低于 100ms 归零退出节流），成功同时清零连击计数。正常服务器永不激活，零惩罚。
- **备选 1——固定全量 pacing**：否决（同 D2 备选 1 理由）。
- **备选 2——令牌桶持久化跨轮配额**：否决。跨轮状态引入持久化与失效问题，上架窗口不需要；运行内自适应已覆盖单轮风暴。
- **备选 3——并发下载**：否决（同 D2 备选 3）。
- 参数（1000/×0.8/100/30000）集中在类头部常量，验收观察后可单点微调。

### D7 持续限流熔断早停：连续 3 次耗尽即结束本轮

- **选定**：节流激活状态下**连续** 3 个请求仍重试耗尽于限流（成功会清零连击），判定服务商硬限流窗口（或小时配额耗尽）：传输层置 `hardThrottled`，后续请求立即抛 `THROTTLED_ABORT`；引擎在 `uploadOne`/远端循环/墓碑循环捕获该错误后向上传播跳出各阶段，`run()` 汇总为 `report.throttled` 与「服务器限流，本轮提前结束，剩余条目下次同步继续」文案。未处理条目保持既有语义（远端条目下轮再拉、dirty 条目下轮再传），天然断点续传。
- **备选 1——不做早停，靠节流磨完**：否决。硬限流窗口内每个请求仍要烧 3 次尝试 + 退避，最坏时长不可控；早停把最坏时长压到「3 次耗尽 + 后续瞬败」。
- **备选 2——按剩余条目数阈值早停**：否决。计数阈值与服务商行为无关、难解释；「连续耗尽」直接对应服务器仍在拒绝的事实。

## Risks / Trade-offs

- [重度限流下单轮同步时长拉长（每实体最坏 3.5s 退避 + Retry-After≤5s）] → Retry-After 5s 上限保证单请求等待有界；同步是手动触发且 `BUSY` 防重入；失败的实体保持 dirty，下一轮续传。
- [PUT 已写入但响应丢失，重试撞 412] → 不重试 412，该轮失败、下一轮 LWW 收敛；无数据损坏风险（内容相同）。
- [文件夹先行后，书签阶段仍可能部分失败] → 由 D2 重试收敛；验收口径以「文件夹全部落远端 + 书签最终（允许跨轮）零积压」为准。
- [重试掩盖持续性故障（如配额耗尽表现为 503）] → 3 次上限 + 失败报告保留可辨识文案，不静默吞错。

## Migration Plan

纯客户端行为变更，无数据/schema/远端结构迁移，随版本直接发布；回滚即 revert 对应提交。存量 `remote_etag`/dirty 状态与新逻辑完全兼容（失败实体维持 dirty 的既有语义不变）。

## Open Questions
